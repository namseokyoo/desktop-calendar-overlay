# Desktop Calendar Overlay v0.8 → v1.0 Development Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Move the current v0.7.1 portfolio-ready Windows overlay from developer/tester Google Calendar integration to a credible v1.0 public desktop release.

**Architecture:** Keep the app as a local-first .NET 8 WPF desktop app. Do not introduce a backend before v1.0. Google Calendar remains behind `ICalendarService` / `IGoogleCalendarIntegration`, with OAuth/token/storage implementation details isolated behind services so the app can support both developer BYO credentials and official release credentials.

**Tech Stack:** .NET 8 WPF, Windows x64 self-contained release, Google Calendar API, local Windows protected storage, GitHub Actions Windows release workflow.

---

## Product stance

### Recommended OAuth sequence

1. **v0.8:** Keep current BYO Desktop OAuth JSON flow, but label it clearly as developer/tester mode.
2. **v0.9:** Add the app-side foundations required for a real public OAuth path: secure token storage, clearer auth UX, privacy/security documentation, and release QA automation.
3. **v0.95 / RC:** Prepare and run Google OAuth verification for an official app-owned OAuth client.
4. **v1.0:** Ship public release only after OAuth verification, privacy policy, release artifact, and Windows QA gates are green.

### Explicit non-goals before v1.0

- No backend OAuth broker unless the product direction changes into SaaS/web/mobile.
- No service-account calendar integration for consumer Gmail users.
- No repeat-event authoring or attendee/invitation workflow.
- No user calendar data collection, server sync, or analytics containing event content.

## Milestone v0.8 — Developer/Test Release Hardening

**Release label:** `v0.8.0-developer-test`

**Core decision:** This is not yet a normal consumer release. It is a Windows desktop MVP for selected testers who can provide Google Desktop OAuth credentials.

### Acceptance criteria

- README states that Google integration is currently developer/tester mode.

## Milestone v0.9 — Public-Readiness Foundation

**Purpose:** Prepare the app for a real public OAuth client and less fragile release quality.

**Release label:** `v0.9.0-public-readiness`

**Core decision:** Still may be distributed to beta testers, but implementation should now match the v1.0 trust model.

### Acceptance criteria

- Token storage is behind an interface and uses OS-protected storage or DPAPI, not plain local folders for refresh tokens.
- OAuth client loading is abstracted so official app-owned client configuration can replace BYO JSON without changing UI/business logic.
- A test project exists for settings, routing, date/event mapping, and failure cases.
- Privacy policy draft exists and matches actual app behavior.
- QA checklist covers install/extract, first launch, connect, CRUD, disconnect, restart, display scaling, and release artifact audit.

### Tasks

#### Task 1: Introduce credential/token storage abstraction

**Objective:** Separate secret handling from Google API code.

**Files:**
- Create: `src/DesktopCalendarOverlay/Services/ITokenStore.cs`
- Create: `src/DesktopCalendarOverlay/Services/LocalGoogleTokenStore.cs`
- Modify: `src/DesktopCalendarOverlay/Services/GoogleCalendarService.cs`

**Implementation notes:**

Interface shape:

```csharp
public interface ITokenStore
{
    Task<bool> HasTokenAsync(CancellationToken cancellationToken = default);
    Task DeleteAsync(CancellationToken cancellationToken = default);
}
```

Keep the first implementation compatible with current Google SDK storage, then prepare a second protected-storage implementation if needed.

**Verification:**

- Existing connect/disconnect behavior still works.
- Token deletion is called only through `ITokenStore`.

#### Task 2: Add OAuth client provider abstraction

**Objective:** Make BYO JSON and future official client config swappable.

**Files:**

- Privacy policy is published at a stable URL.
- OAuth verification submission package is prepared.

- BYO JSON mode remains available only as an explicit advanced/developer fallback.
